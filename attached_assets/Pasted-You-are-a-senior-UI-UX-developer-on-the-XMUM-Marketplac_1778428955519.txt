BUG 1 — NOTIFICATIONS WRITE RULE BLOCKS sendNewMessageNotification
═══════════════════════════════════════════════
PROBLEM: The current Firestore rule for notifications is:
  match /users/{userId}/notifications/{notifId} {
    allow read: if isOwner(userId);
    allow write: if isOwner(userId) || isEditor();
  }

sendNewMessageNotification writes to users/{recipientUid}/notifications
but is called by the SENDER (not the recipient and not an admin).
The sender's uid !== recipientUid, so isOwner(userId) fails.
The sender is not an editor, so isEditor() also fails.
Result: every new message notification silently fails with
"permission-denied" — the try/catch hides it.

FIX: In firestore.rules, update the notifications rule to also
allow ANY authenticated XMUM email user to write notifications
to other users (for system-generated notifications like new_message):

  match /users/{userId}/notifications/{notifId} {
    allow read: if isOwner(userId);
    allow write: if isOwner(userId)
                 || isEditor()
                 || isXmuEmail(); // ← allows peer notifications
  }

This is safe because: (a) only @xmu.edu.my accounts can write,
(b) users can only read their OWN notifications (isOwner on read),
(c) the worst case is someone spamming another user's notifications —
add a Firestore rate limit via security rules if this becomes an
issue later.
