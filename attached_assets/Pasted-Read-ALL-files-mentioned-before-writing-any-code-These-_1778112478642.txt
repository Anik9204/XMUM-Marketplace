BUG 1 — .replit HAS DUPLICATE externalPort 80 MAPPINGS

The .replit file currently has FIVE port entries:

BUG 3 — deleteListing USES WRONG STORAGE URL FORMAT
=================================================================

FILE: src/lib/listings.ts — deleteListing function

Current code:
  listing.photos.map((url) =>
    deleteObject(ref(storage, url))
  )

The photos array stores FULL Firebase Storage download 
URLs like:
  https://firebasestorage.googleapis.com/v0/b/xmum--market
  .firebasestorage.app/o/listings%2F...?alt=media&token=...

But ref(storage, url) expects EITHER a storage path 
(listings/userId/filename.png) OR a gs:// URL.
Passing a full https download URL to ref() will FAIL 
silently — deleteObject will throw an error that is 
swallowed by the catch block, leaving orphan files 
in Storage.

FIX: Add a helper to extract the Storage path from the 
download URL, and use it before calling deleteObject:

  function storagePathFromUrl(url: string): string | null {
    try {
      const match = url.match(/\/o\/(.+?)(\?|$)/);
      if (!match) return null;
      return decodeURIComponent(match[1]);
    } catch {
      return null;
    }
  }

Then update deleteListing:

  listing.photos.map((url) => {
    const path = storagePathFromUrl(url);
    if (!path) return Promise.resolve();
    return deleteObject(ref(storage, path)).catch((err) => {
      if (err?.code !== 'storage/object-not-found') throw err;
    });
  })

Apply the SAME fix to deleteAccount in userProfile.ts 
Step 4 where listing photos are deleted.

Also fix Step 5 in deleteAccount — avatar deletion:

  Current:
    deleteObject(ref(storage, profile.avatarUrl))
  
  profile.avatarUrl is also a full download URL.
  Fix:
    const avatarPath = storagePathFromUrl(profile.avatarUrl)
    if (avatarPath) {
      await deleteObject(ref(storage, avatarPath)).catch(...)
    }

BUG 4 — getUserListings REQUIRES A COMPOSITE INDEX
         THAT MAY NOT EXIST
=================================================================

FILE: src/lib/listings.ts — getUserListings function

Current primary query:
  where('userId', '==', userId),
  where('isArchived', '==', false),
  orderBy('createdAt', 'desc')

This requires a composite index:
  userId ASC + isArchived ASC + createdAt DESC

This index was never mentioned in the setup docs and 
likely does not exist in Firebase Console. Without it 
the query throws failed-precondition and falls to the 
fallback — but the fallback query:
  where('userId', '==', userId),
  where('isArchived', '==', false)
  
still requires a composite index (userId + isArchived).

FIX the fallback to be truly index-free:
  const q2 = query(
    collection(db, 'listings'),
    where('userId', '==', userId),
    limit(40)
  )
  const snap = await getDocs(q2)
  const docs = snap.docs.map(mapDoc)
  return docs
    .filter(l => l.isArchived === false)
    .sort((a, b) => b.createdAt - a.createdAt)

A single where('userId') equality filter does NOT 
require a composite index — only the combination 
with other filters or orderBy does.

Also add this second index to the Firebase Console 
documentation in replit.md:
  Collection: listings
  Fields: userId ASC + isArchived ASC + createdAt DESC
  Scope: Collection

=================================================================

FILE: src/pages/PostPage.tsx vs Firebase Storage Rules

PostPage.tsx validates: MAX_FILE_BYTES = 10 * 1024 * 1024 (10MB)
Storage rules enforce:  request.resource.size < 5 * 1024 * 1024 (5MB)

A user can pass the client-side validation with a 6MB

security rule with a permission-denied error.

FIX: Change PostPage.tsx to match the Storage rule:
  const MAX_FILE_BYTES = 5 * 1024 * 1024; // 5MB

Also update the UI hint text from:
  "Max 10 MB per photo"
to:
  "Max 5 MB per photo"

IMPROVEMENT 2 — NO LOADING STATE ON PROFILE TAB 
               SWITCHING BACK FROM SETTINGS
=================================================================

FILE: src/pages/ProfilePage.tsx

When user navigates: Profile → Settings → back to Profile,
the listings reload from scratch (getUserListings is called 
again in useEffect). On slow connections this shows a 
skeleton flash every time.

FIX: Cache the listings in a ref so they survive 
navigation within the same session:

  const listingsCache = useRef<Listing[]>([]);
  
  useEffect(() => {
    if (!user) return;
    if (listingsCache.current.length > 0) {
      setListings(listingsCache.current);
      return; // use cache, skip fetch
    }
    setLoading(true);
    getUserListings(user.uid)
      .then((data) => {
        listingsCache.current = data;
        setListings(data);
      })
      .finally(() => setLoading(false));
  }, [user]);
