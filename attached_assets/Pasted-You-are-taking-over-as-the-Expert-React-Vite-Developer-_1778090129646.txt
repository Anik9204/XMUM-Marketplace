SECTION 3 — CRITICAL FIREBASE INITIALIZATION RULE
=================================================================

Because this app runs inside Replit's cloud proxy environment, 
Firestore MUST be initialized with long-polling. The firebase.ts 
file must use initializeFirestore (NOT getFirestore) with this 
exact option:

  import { initializeFirestore } from 'firebase/firestore';

  export const db = initializeFirestore(app, {
    experimentalAutoDetectLongPolling: true,
  });

If firebase.ts uses getFirestore() instead, replace it with 
the above. This is non-negotiable — without it, ALL Firestore 
reads and writes will silently fail or hang in Replit.

Also confirm:
- A singleton guard is in place (getApps().length check) to 
  prevent double-initialization on Vite HMR hot reloads.
- Offline persistence is enabled using persistentLocalCache 
  with persistentSingleTabManager.

SECTION 4 — FIREBASE SECURITY RULES (ALREADY DEPLOYED — DO NOT CHANGE)
=================================================================

These rules are live on the Firebase server. Never suggest 
frontend code that bypasses them, and never attempt to 
modify them.

FIRESTORE RULES:
───────────────
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /users/{userId} {
      allow read: if true;
      allow write: if request.auth != null 
                   && request.auth.uid == userId;
    }
    match /listings/{listingId} {
      allow read: if true;
      allow create: if request.auth != null
                    && request.auth.token.email
                       .matches('.*@xmu\\.edu\\.my');
      allow update, delete: if request.auth != null
                    && request.auth.uid == resource.data.userId;
    }
  }
}

STORAGE RULES:
──────────────
rules_version = '2';
service firebase.storage {
  match /b/{bucket}/o {
    match /listings/{userId}/{allPaths=**} {
      allow read: if true;
      allow create, update: if request.auth != null
                   && request.auth.token.email
                      .matches('.*@xmu\\.edu\\.my')
                   && request.resource.size < 5 * 1024 * 1024
                   && request.resource.contentType
                      .matches('image/.*');
      allow delete: if request.auth != null
                   && request.auth.uid == userId
                   && request.auth.token.email
                      .matches('.*@xmu\\.edu\\.my');
    }
    match /avatars/{userId}/{allPaths=**} {
      allow read: if true;
      allow create, update, delete: if request.auth != null
                   && request.auth.uid == userId
                   && request.auth.token.email
                      .matches('.*@xmu\\.edu\\.my')
                   && (request.method == 'delete' || (
                      request.resource.size < 5 * 1024 * 1024
                      && request.resource.contentType
                         .matches('image/.*')));
    }
  }
}

KEY IMPLICATIONS OF THESE RULES:
- Only @xmu.edu.my email addresses can create listings or 
  upload files. The frontend must never try to bypass this.
- Listing updates and deletes are owner-only (auth.uid must 
  match resource.data.userId).
- Avatar deletes and uploads are owner-only (auth.uid must 
  match the {userId} path segment).
- ALL Storage deletes for a user's files MUST happen while 
  the user is still authenticated — before deleteUser() is 
  called. If deleteUser() fires first, all subsequent 
  deleteObject() calls will fail with permission errors.
