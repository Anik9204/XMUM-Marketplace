> ## ISSUE 3 — WhatsApp-Style Unread Message Counting (1 notification per conversation, not per message)
>
> ### Root Cause
> In `src/lib/messaging.ts`, the `sendMessage` function calls `sendNewMessageNotification(...)` on every single message sent:
> ```ts
> // line ~106
> await sendNewMessageNotification(otherUid, senderName, listingTitle);
> ```
> This fires a new notification document into Firestore for **every message**, so 9 rapid messages → 9 notification items. The badge count in `subscribeToUnreadCount` sums the raw `unreadCount` integers, which are also incremented per message, causing the badge to show `9` instead of `1`.
>
> The badge count behaviour (`subscribeToUnreadCount`) is actually correct for showing total unread messages — but the **notification bell** should show conversations with unread messages, not total messages. Fix both layers:
>
> ### Fix — Layer 1: One notification per conversation, not per message
>
> **File: `src/lib/messaging.ts`**
>
> Find the `sendMessage` function. The `sendNewMessageNotification` call currently runs unconditionally. Change it to only fire when the **recipient currently has zero unread messages** in this conversation (i.e., this is the first unread message in the thread):
>
> ```ts
> // BEFORE (inside sendMessage, after the updateDoc call):
> await sendNewMessageNotification(otherUid, senderName, listingTitle);
>
> // AFTER — only notify if this is the FIRST unread message in this conversation:
> const prevUnread = convSnap.data()?.unreadCount?.[otherUid] ?? 0;
> if (prevUnread === 0) {
>   await sendNewMessageNotification(otherUid, senderName, listingTitle);
> }
> ```
>
> IMPORTANT: The variable `convSnap` is already fetched earlier in `sendMessage` (it's used to get `unreadCount` for the `updateDoc` call). Do NOT re-fetch it. Read `prevUnread` from the **same `convSnap`** that already exists in that function scope, before the `updateDoc` runs (since `updateDoc` modifies it).
>
> ### Fix — Layer 2: Badge shows number of conversations with unread messages, not total message count
>
> **File: `src/lib/messaging.ts`** — find `subscribeToUnreadCount`:
>
> ```ts
> // CURRENT — sums all unread message counts (shows "9" for 9 messages in 1 chat):
> const total = snap.docs.reduce((sum, d) => {
>   const count = d.data()?.unreadCount?.[uid] ?? 0;
>   return sum + (typeof count === "number" ? count : 0);
> }, 0);
> callback(total);
>
> // REPLACE WITH — counts conversations that have at least 1 unread (WhatsApp style):
> const total = snap.docs.filter((d) => {
>   const count = d.data()?.unreadCount?.[uid] ?? 0;
>   return typeof count === "number" && count > 0;
> }).length;
> callback(total);
> ```
>
> This means if one person sends you 9 messages in one chat, the badge shows `1` (one conversation has unread), not `9`. If two separate conversations each have unread messages, the badge shows `2`.
>
> **File: `src/components/NotificationBell.tsx`** — check how it counts unread notifications. If it counts individual notification documents (each message = 1 doc), apply the same deduplication: only count notification documents with `type: "new_message"` once **per conversation** (group by `conversationId` if that field exists, or just count unread non-message notifications + at most 1 per conversation). If `conversationId` is not stored on the notification document, the simplest safe fix is: don't count `new_message` notifications individually — instead use the `unreadConversations` count from `subscribeToUnreadCount` for the message badge, and only show the notification bell count for non-message notification types. Check the notification document structure before deciding.

> ## ISSUE 4 — AvatarCropModal: Auto-Zoom Fix + Ghost Overlay Fix
>
> ### File to edit: `src/components/AvatarCropModal.tsx`
> **Who uses it:** Only `src/pages/SettingsPage.tsx` (controlled via `cropFile` state — the modal mounts when `cropFile !== null` and unmounts when `setCropFile(null)` is called). No other files import this component.
>
> ### Bug A — Image Loads Zoomed In
>
> **Root Cause:** In the `useEffect` that loads the image (line ~79):
> ```ts
> const scale = Math.max(canvas.width / img.naturalWidth, canvas.height / img.naturalHeight);
> scaleRef.current = Math.max(1, scale);
> ```
> `Math.max(canvas.width / w, canvas.height / h)` is the **cover** algorithm — it scales the image up to fill the canvas. For a 4000×3000 phone photo on a 320×320 canvas, this gives `320/4000 = 0.08`, but then `Math.max(1, 0.08) = 1` — so the scale clamps to `1` and the 4000px image is drawn at full size, appearing massively zoomed in.
>
> **Fix:** Change the scale algorithm to **contain** (fit the image inside the circle) and allow the scale to go below 1:
> ```ts
> // REPLACE these two lines:
> const scale = Math.max(canvas.width / img.naturalWidth, canvas.height / img.naturalHeight);
> scaleRef.current = Math.max(1, scale);
>
> // WITH (contain = fit entirely inside the crop circle, scale can be < 1):
> const circleDiameter = Math.min(canvas.width, canvas.height) * 0.85;
> const scale = Math.min(circleDiameter / img.naturalWidth, circleDiameter / img.naturalHeight);
> scaleRef.current = scale; // no Math.max(1, ...) clamp — allow scaling down
> ```
>
> Also update the `handleWheel` and `handleTouchMove` zoom clamps from `Math.max(1, ...)` to `Math.max(0.1, ...)` so the user can zoom out:
> ```ts
> // handleWheel:
> scaleRef.current = Math.min(4, Math.max(0.1, scaleRef.current + delta));
>
> // handleTouchMove:
> scaleRef.current = Math.min(4, Math.max(0.1, pinchRef.current.origScale * ratio));
> ```
>
> ### Bug B — Ghost Overlay After Cancel
>
> **Root Cause:** The modal is unmounted in `SettingsPage.tsx` by calling `setCropFile(null)` (triggered by `onCancel`). In React, this removes the component from the DOM, which should clean up the overlay. However, the `objectUrl` cleanup in the `useEffect` return runs AFTER the state update that caused the unmount, which can leave the canvas drawing loop in a torn state and cause a visual glitch on some browsers.
>
> **Fix:** In `AvatarCropModal.tsx`, add an explicit reset in the `onCancel` handlers to revoke the object URL and clear refs before the parent unmounts:
>
> Create a `handleCancel` wrapper function inside the component:
> ```ts
> const handleCancel = useCallback(() => {
>   // Revoke the object URL immediately to prevent memory leak and visual ghost
>   if (objectUrlRef.current) {
>     URL.revokeObjectURL(objectUrlRef.current);
>     objectUrlRef.current = null;
>   }
>   // Clear the canvas so no ghost frame remains if unmount is async
>   const canvas = canvasRef.current;
>   if (canvas) {
>     const ctx = canvas.getContext("2d");
>     ctx?.clearRect(0, 0, canvas.width, canvas.height);
>   }
>   imgRef.current = null;
>   onCancel();
> }, [onCancel]);
> ```
>
> Then replace ALL occurrences of `onClick={onCancel}` in the JSX with `onClick={handleCancel}`. There are exactly **two** — the X button in the header and the "Cancel" text button at the bottom.
>
> Also, update the `useEffect` cleanup to guard against double-revoke:
> ```ts
> return () => {
>   if (objectUrlRef.current) {
>     URL.revokeObjectURL(objectUrlRef.current);
>     objectUrlRef.current = null;
>   }
> };
> ```
