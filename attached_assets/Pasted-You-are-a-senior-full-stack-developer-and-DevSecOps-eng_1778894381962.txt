═══════════════════════════════════════════════════
CONTEXT — Architecture of the audit log
═══════════════════════════════════════════════════

Every significant admin write action (delete, ban, role change, approve,
reject, archive, feature, suspend) will write a document to a new Firestore
collection called `adminAuditLogs`. Each document has this shape:

  {
    actorUid:    string,   // admin's uid
    actorEmail:  string,   // admin's email
    action:      string,   // machine-readable action key e.g. "listing_deleted"
    label:       string,   // human-readable description e.g. 'Deleted listing "fffffff"'
    targetId:    string,   // id of the affected document
    targetType:  string,   // "listing" | "user" | "shop" | "report" | "shopAd"
    targetLabel: string,   // human-readable target e.g. listing title or user email
    createdAt:   number,   // Date.now()
  }

The audit log is WRITE-ONLY for admin users (they can create but not edit
or delete — not even admins). Only admins can READ it. This makes it
tamper-evident: once logged, no one can erase the trail.
