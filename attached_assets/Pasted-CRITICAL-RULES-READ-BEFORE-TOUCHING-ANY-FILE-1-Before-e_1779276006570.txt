PART 4 — Fix: sendMessage race condition on unreadCount

FILE TO EDIT: artifacts/xmum-market/src/lib/messaging.ts

THE BUG:
In sendMessage, the code does a getDoc to read the current unreadCount, then uses that
snapshot value to manually increment: unreadCount[otherUid] + 1. If two messages are sent
concurrently (rapid tapping, two open tabs), both reads see the same stale count and both
write the same incremented value — effectively dropping one increment. The notification
logic also reads prevUnread from the same stale snapshot.

THE FIX:
First, add increment to the firebase/firestore import at the top of messaging.ts.
Check what is already imported from "firebase/firestore" — add increment to that list
if it is not already there.

Then find the sendMessage function. The current update block looks like this:

  const convSnap = await getDoc(convRef);
  const prevUnread = convSnap.data()?.unreadCount?.[otherUid] ?? 0;
  await updateDoc(convRef, {
    lastMessage: trimmed.slice(0, 80),
    lastMessageAt: Date.now(),
    [`unreadCount.${otherUid}`]: (convSnap.data()?.unreadCount?.[otherUid] ?? 0) + 1,
  });

  try {
    if (prevUnread === 0) {
      await sendNewMessageNotification(
        otherUid,
        senderName,
        convSnap.data()?.listingTitle ?? "a listing"
      );
    }
  } catch {}

Replace it with:

  await updateDoc(convRef, {
    lastMessage: trimmed.slice(0, 80),
    lastMessageAt: Date.now(),
    [`unreadCount.${otherUid}`]: increment(1),
  });

  try {
    await sendNewMessageNotification(
      otherUid,
      senderName,
      ""
    );
  } catch {}

IMPORTANT NOTES on the replacement:
- We remove the getDoc entirely — it was only needed to read prevUnread and listingTitle.
  increment(1) is atomic and does not need a read-first.
- The prevUnread === 0 guard (to send notification only on first unread) was a nice-to-have
  but caused the race. Removing it means a notification fires on every message, not just the
  first unread one. This is acceptable — the notification system already deduplicates in
  addNotification and the bell only shows the latest.
- The listingTitle is passed as empty string "" because we no longer fetch the conversation
  snapshot. Check the sendNewMessageNotification function signature — it accepts
  (recipientUid: string, senderName: string, listingTitle: string). Passing "" is safe,
  the notification body will show "Re: " which is slightly degraded but not broken.
  If you want to preserve listingTitle: add listingTitle as a parameter to sendMessage
  and thread it through from MessagesPage.tsx where the activeConv.listingTitle is available.
  Check MessagesPage.tsx to see how sendMessage is called and whether adding the parameter
  is straightforward. If it requires touching more than 3 lines in MessagesPage, just use "".
