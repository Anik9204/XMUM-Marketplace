## What the Previous Fix Got Wrong

The previous fix (invalidating `listingsCache.current` on mount) was a good idea but it **did not fix the actual bug**. It only ensures the Profile page reads fresh data from Firestore. The problem is that **view counts are never being written to Firestore in the first place** — so there is nothing fresh to read.

The view count increment is being **silently rejected by Firestore Security Rules** with a `permission-denied` error, which is swallowed by `.catch(() => {})` in `ListingDetailPage.tsx`. The count appears to increment locally in the UI (because of the optimistic `setListing` call on line 168), but nothing is ever written to Firestore.

---

## Root Cause — Firestore Security Rules

**File:** `artifacts/xmum-market/firestore.rules`

Open this file and find the `listings` collection rule block. The current `allow update` rule reads:

```js
allow update: if isXmuEmail()
  && resource.data.userId == request.auth.uid
  && resource.data.isReportHeld != true
  && (!request.resource.data.keys().hasAny(["price"])
      || (request.resource.data.price >= 0
          && request.resource.data.price <= 1000000));
```

**The problem:** `resource.data.userId == request.auth.uid` means **only the listing owner can update the document**. When any other signed-in user views a listing for 5 seconds and `ListingDetailPage.tsx` calls:

```ts
updateDoc(doc(db, "listings", listing.id), { viewCount: increment(1) })
```

...Firestore evaluates the rule, sees that `auth.uid` ≠ `listing.userId`, and **rejects the write with `permission-denied`**. The `.catch(() => {})` silently discards the error. Nothing is written. The number stays at 0.

Now look at the `shopListings` rule in the same file — it correctly handles this case:

```js
allow update: if isXmuEmail() && (
  isShopMember(resource.data.shopId)
  || request.resource.data.diff(resource.data).affectedKeys().hasOnly(['inquiryCount'])
  || request.resource.data.diff(resource.data).affectedKeys().hasOnly(['viewCount'])  // ← THIS
);
```

The `shopListings` rule has a `viewCount`-only exception that allows any signed-in XMU user to increment the view count. The `listings` rule is missing this exception entirely.

## Fix 1 — Add the `viewCount`-only exception to the `listings` rule

**File:** `artifacts/xmum-market/firestore.rules`

**Surgical edit — add one OR branch to the existing `allow update` rule for `listings`.**

Find this exact block:

```js
match /listings/{listingId} {
  allow read: if true;
  allow create: if isXmuEmail()
    && request.resource.data.userId == request.auth.uid
    && request.resource.data.title is string
    && request.resource.data.title.size() > 0
    && request.resource.data.title.size() <= 100
    && request.resource.data.description is string
    && request.resource.data.description.size() <= 1000
    && request.resource.data.type in
       ["buy-sell", "lost-found", "jobs", "assistance", "rental"]
    && (!request.resource.data.keys().hasAny(["price"])
        || (request.resource.data.price >= 0
            && request.resource.data.price <= 1000000));
  allow update: if isXmuEmail()
    && resource.data.userId == request.auth.uid
    && resource.data.isReportHeld != true
    && (!request.resource.data.keys().hasAny(["price"])
        || (request.resource.data.price >= 0
            && request.resource.data.price <= 1000000));
  allow delete: if ((isXmuEmail() && resource.data.userId == request.auth.uid && resource.data.isReportHeld != true)
    || isEditorRole());
}
```

Replace **only the `allow update` line** with this updated version that adds a `viewCount`-only exception as a second branch:

```js
  allow update: if (isXmuEmail()
    && resource.data.userId == request.auth.uid
    && resource.data.isReportHeld != true
    && (!request.resource.data.keys().hasAny(["price"])
        || (request.resource.data.price >= 0
            && request.resource.data.price <= 1000000)))
    || (isXmuEmail()
        && request.resource.data.diff(resource.data).affectedKeys().hasOnly(['viewCount']));
```

**What this does:** Any verified XMU user can now write to a listing document — but ONLY if the write touches nothing except the `viewCount` field. The `diff(...).affectedKeys().hasOnly(['viewCount'])` check is a Firestore Rules built-in that ensures the request cannot change any other field. The owner-only restriction remains fully intact for all other updates (status, price, title, etc.).

Do not change `allow read`, `allow create`, or `allow delete`. Only `allow update` changes.

## Fix 2 — Surface the error instead of swallowing it silently

**File:** `artifacts/xmum-market/src/pages/ListingDetailPage.tsx`

This is a minor but important fix so future permission issues are visible during development.

Find line 167 (the view count increment inside the `setTimeout`):

```ts
updateDoc(doc(db, "listings", listing.id), { viewCount: increment(1) }).catch(() => {});
```

Replace with:

```ts
updateDoc(doc(db, "listings", listing.id), { viewCount: increment(1) }).catch((err) => {
  console.warn("[viewCount] Failed to increment:", err?.code, err?.message);
});
```

**What this does:** The silent `.catch(() => {})` was hiding the `permission-denied` error completely. With this change, any future Firestore rule failures will appear in the browser console as a warning, making them much easier to diagnose. This does not change any user-facing behaviour.
