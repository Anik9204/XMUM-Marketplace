SECTION 3 — CRITICAL FIREBASE INITIALIZATION RULE
=================================================================

This project was developed in Replit and the Firebase 
initialization has a critical requirement that must be 
preserved even in VS Code.

Firestore MUST be initialized with experimentalAutoDetectLongPolling 
set to true. This was required for Replit's proxy environment 
and must remain in place to keep the app consistent with 
production. Do not remove it.

The firebase.ts file must use initializeFirestore (NOT 
getFirestore) like this:

  import { initializeFirestore } from 'firebase/firestore';

  export const db = initializeFirestore(app, {
    experimentalAutoDetectLongPolling: true,
  });

If firebase.ts uses getFirestore() instead, that is a bug — 
flag it but do not change it without being explicitly asked.

Also confirm:
- A singleton guard exists (getApps().length check) to 
  prevent double-initialization on Vite HMR reloads.
- Offline persistence is enabled via persistentLocalCache 
  with persistentSingleTabManager.

SECTION 4 — FIREBASE SECURITY RULES (LIVE — DO NOT CHANGE)
=================================================================

These rules are already deployed to the Firebase project. 
They are the law. Never write frontend code that violates 
or tries to bypass them. Never suggest changing them.

FIRESTORE RULES:
────────────────
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /users/{userId} {
      allow read: if true;
      allow write: if request.auth != null 
                   && request.auth.uid == userId;
    }
    match /listings/{listingId} {
      allow read: if true;
      allow create: if request.auth != null
                    && request.auth.token.email
                       .matches('.*@xmu\\.edu\\.my');
      allow update, delete: if request.auth != null
                    && request.auth.uid == resource.data.userId;
    }
  }
}

STORAGE RULES:
──────────────
rules_version = '2';
service firebase.storage {
  match /b/{bucket}/o {
    match /listings/{userId}/{allPaths=**} {
      allow read: if true;
      allow create, update: if request.auth != null
                   && request.auth.token.email
                      .matches('.*@xmu\\.edu\\.my')
                   && request.resource.size < 5 * 1024 * 1024
                   && request.resource.contentType
                      .matches('image/.*');
      allow delete: if request.auth != null
                   && request.auth.uid == userId
                   && request.auth.token.email
                      .matches('.*@xmu\\.edu\\.my');
    }
    match /avatars/{userId}/{allPaths=**} {
      allow read: if true;
      allow create, update, delete: if request.auth != null
                   && request.auth.uid == userId
                   && request.auth.token.email
                      .matches('.*@xmu\\.edu\\.my')
                   && (request.method == 'delete' || (
                      request.resource.size < 5 * 1024 * 1024
                      && request.resource.contentType
                         .matches('image/.*')));
    }
  }
}

KEY IMPLICATIONS:
- Only @xmu.edu.my emails can create listings or upload files.
- Listing updates/deletes: only the owner (auth.uid must match 
  resource.data.userId in the Firestore document).
- Avatar operations: only the owner (auth.uid must match the 
  {userId} segment in the Storage path).
- CRITICAL DELETION ORDER: When deleting a user account, ALL 
  Storage file deletes (avatars + listing images) MUST complete 
  before deleteUser() is called. If Auth is deleted first, all 
  subsequent Storage deleteObject() calls fail silently with 
  permission errors because the auth token is gone.

SECTION 6 — CODING RULES — ALWAYS FOLLOW THESE
=================================================================

1. NEVER change Firebase Firestore or Storage security rules.

2. NEVER hardcode Firebase config — always import.meta.env.
   VITE_FIREBASE_*

3. ALWAYS keep experimentalAutoDetectLongPolling: true in 
   firebase.ts — do not remove or comment it out.

4. ROUTING: wouter only.
   Correct imports: useLocation, navigate, Link, Route, Switch 
   from 'wouter'. Never import from 'react-router-dom', 
   'next/navigation', or any other routing library.

5. TAILWIND v4 DARK MODE:
   - Dark mode variant is defined via @custom-variant in 
     index.css — NOT via darkMode: 'class' in tailwind.config
   - Do NOT add or modify tailwind.config for dark mode
   - Use dark: prefix classes as normal in JSX
   - Standard dark palette: 
       Page bg:      dark:bg-slate-950
       Header/nav:   dark:bg-slate-900
       Cards/modals: dark:bg-slate-800
       Inputs:       dark:bg-slate-700
       Borders:      dark:border-slate-600 / dark:border-slate-700
       Text primary: dark:text-slate-100
       Text muted:   dark:text-slate-400

6. i18n: Every new user-visible string must be added to 
   src/lib/i18n.ts under BOTH 'en' and 'zh' keys.

7. Firestore writes: Always use updateDoc for partial updates.
   Never use setDoc without { merge: true } — it silently 
   overwrites the entire document wiping other fields.

8. TypeScript: Run tsc --noEmit after every change. 
   Fix all type errors before saying you are done. 
   Zero new TypeScript errors is the acceptance criteria.

9. Firestore deleteDoc: Always race against a 6-second timeout.
   Offline persistence in Firestore can block deleteDoc calls 
   indefinitely. Use:
     const withTimeout = (p: Promise<any>, ms: number) =>
       Promise.race([p, new Promise(res => setTimeout(res, ms))]);

10. Parallel deletes: Always use Promise.allSettled() — never 
    Promise.all(). allSettled never throws even if one item 
    fails; Promise.all() aborts the whole batch on first error.

11. Touch targets: All interactive elements (buttons, links, 
    nav items) must have min-h-[44px] for mobile usability.

12. Image uploads: Always validate before uploading —
    - File must be image/* MIME type
    - File must be under 5MB
    These match the Storage rules and must be enforced 
    client-side too for good UX.
