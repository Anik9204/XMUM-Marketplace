BUG 1 — Storage delete rule missing → listing delete always fails with permission-denied
═══════════════════════════════════════════════════════

FILE: artifacts/xmum-market/storage.rules

PROBLEM: The `listings/{userId}/...` match block only has `allow write:` which covers upload/update but NOT delete. Firebase Storage treats delete as a separate operation. When deleteListing() in listings.ts calls deleteObject() on a photo, Storage rejects it, the whole delete flow aborts, and the user sees "Permission denied".

FIX: In the `match /listings/{userId}/{allPaths=**}` block, split `allow write:` into separate `allow create, update:` and `allow delete:` rules. The delete rule only needs to check that the requester is the owner of that userId path (no request.resource checks — request.resource is unavailable on delete).

The block should become:

    match /listings/{userId}/{allPaths=**} {
      allow read: if true;
      allow create, update: if request.auth != null
                   && request.auth.token.email.matches('.*@xmu\\.edu\\.my')
                   && request.resource.size < 5 * 1024 * 1024
                   && request.resource.contentType.matches('image/.*');
      allow delete: if request.auth != null
                   && request.auth.uid == userId;
    }

IMPORTANT: Do not change any other block in storage.rules. Only change the listings block.

After editing, I will manually deploy via: Firebase Console → Storage → Rules → paste → Publish.

BUG 2 — Edit listing Save fails with "Permission denied. Make sure your email is verified"
═══════════════════════════════════════════════════════

FILE: artifacts/xmum-market/src/pages/EditListingPage.tsx

PROBLEM: The handleSubmit function calls `auth.currentUser?.getIdToken(true)` to force a token refresh, but then discards the result. More importantly, it does NOT call `auth.currentUser?.reload()` first. Firebase Auth stores the user object in memory — `emailVerified` on the in-memory object may be stale if the user verified their email in a different tab or session. Without reload(), the ID token refresh may still use the stale in-memory state. Firestore then evaluates `request.auth.token.email_verified` from the JWT which reflects the old unverified state, causing permission-denied on the update.

FIX: In handleSubmit, replace the existing token-refresh line:

FIND this exact line inside the try block at the top of handleSubmit:
      await withTimeout(auth.currentUser?.getIdToken(true) ?? Promise.resolve(""), 10_000, "token-refresh");

REPLACE with these two sequential awaits:
      await withTimeout(auth.currentUser?.reload() ?? Promise.resolve(), 5_000, "token-refresh");
      await withTimeout(auth.currentUser?.getIdToken(true) ?? Promise.resolve(""), 10_000, "token-refresh");

This forces Firebase to re-fetch the user's auth state from the server (including the latest emailVerified flag) and then get a fresh JWT that contains email_verified: true, which Firestore's security rules will then accept.

The `withTimeout` wrapper and the error handler for `"timeout:token-refresh"` already exist — do not change them.
