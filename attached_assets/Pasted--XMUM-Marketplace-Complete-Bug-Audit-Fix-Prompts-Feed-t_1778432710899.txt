## BUG FIX PROMPT 1 OF 10
## Dark Mode Flash on Load (FOUC) + Auto-Enables on Settings Visit

**Root Cause:**
Two separate bugs combine here.

Bug A: `index.html` has no inline script to apply the `dark` class to `<html>` before React hydrates. So users with dark mode saved see a white flash every page load.

Bug B: `useDarkMode` is a plain hook — every component that calls it creates its own isolated `useState`. When `SettingsPage` mounts, it calls `useDarkMode()` and initialises its own `dark` state from localStorage. But since `userHasToggled.current` starts as `false` in this new instance, the `useEffect` that sets the `dark` class runs immediately on mount. If the OS is in dark mode but the user previously set `light`, the Settings instance re-reads and re-applies correctly — but because this is a second instance of the hook, React's state reconciliation triggers a re-render which briefly applies the wrong class. The real fix is to move dark mode into a single shared context.

---

**Paste this entire prompt to Replit:**

```
You are fixing two related dark mode bugs in the XMUM Marketplace app.

## BUG A — Flash of white on load (FOUC)

Open `artifacts/xmum-market/index.html`.

Add this inline script as the VERY FIRST child of <head>, before any other tags:

```html
<script>
  (function () {
    try {
      var theme = localStorage.getItem('xmum-theme');
      if (theme === 'dark' || (!theme && window.matchMedia('(prefers-color-scheme: dark)').matches)) {
        document.documentElement.classList.add('dark');
      }
    } catch (e) {}
  })();
</script>
```

This must be the first tag in <head> so it runs synchronously before any CSS or React loads,
preventing the white flash.

## BUG B — Dark mode state not shared across components

The current `useDarkMode` hook is a plain React hook. Every component that calls it
gets its own isolated useState. This causes SettingsPage to create a new instance on
mount, which can re-apply dark mode incorrectly.

The fix: convert dark mode into a React Context so there is only ONE source of truth.

### Step 1 — Rewrite `artifacts/xmum-market/src/hooks/use-dark-mode.ts`

Replace the entire file with:

```typescript
// This file is now just a re-export for backwards compatibility.
// The real implementation is in DarkModeContext.
export { useDarkMode } from "@/contexts/DarkModeContext";
```

### Step 2 — Create `artifacts/xmum-market/src/contexts/DarkModeContext.tsx`

Create this new file with the following content:

```typescript
import { createContext, useContext, useEffect, useRef, useState, ReactNode } from "react";

interface DarkModeCtx {
  dark: boolean;
  toggle: () => void;
}

const Ctx = createContext<DarkModeCtx>({ dark: false, toggle: () => {} });

export function DarkModeProvider({ children }: { children: ReactNode }) {
  const userHasToggled = useRef(false);

  const [dark, setDark] = useState<boolean>(() => {
    try {
      const stored = localStorage.getItem("xmum-theme");
      if (stored === "dark") return true;
      if (stored === "light") return false;
      return window.matchMedia("(prefers-color-scheme: dark)").matches;
    } catch {
      return false;
    }
  });

  useEffect(() => {
    const root = document.documentElement;
    if (dark) {
      root.classList.add("dark");
    } else {
      root.classList.remove("dark");
    }
    // Only persist to localStorage when the user explicitly clicked the toggle
    if (userHasToggled.current) {
      localStorage.setItem("xmum-theme", dark ? "dark" : "light");
    }
  }, [dark]);

  const toggle = () => {
    userHasToggled.current = true;
    setDark((d) => !d);
  };

  return <Ctx.Provider value={{ dark, toggle }}>{children}</Ctx.Provider>;
}

export function useDarkMode() {
  return useContext(Ctx);
}
```

## BUG FIX PROMPT 2 OF 10
## Page Shake / Jitter on Desktop Scroll (Multiple Sticky Headers)

**Root Cause:**
There are TWO sticky elements stacked:
1. The `<header>` in `Layout.tsx` is `sticky top-0 h-14 sm:h-16`
2. Sub-headers in `HomePage.tsx`, `SearchPage.tsx`, and `ListingDetailPage.tsx` use `sticky top-14 sm:top-16`

On desktop, when the browser scrollbar appears/disappears (because content changes between loading and loaded), it shifts the page width by ~15px. This, combined with stacked sticky elements that depend on exact pixel offsets, causes visible jitter/shake. The sub-headers also create a "fighting sticky" effect — two stacking contexts competing.

The additional issue: `transform` and `will-change` are not set on sticky elements, so the browser can't GPU-composite them, causing repaints on every scroll frame.

## BUG FIX PROMPT 3 OF 10
## Messages Page — Typing Locks Scroll + Textarea Doesn't Shrink

**Root Cause — Scroll Lock:**
The message list area is `flex-1 overflow-y-auto`. The textarea at the bottom uses `rows={1}` with `max-h-32 overflow-y-auto`. When the textarea grows (multi-line typing), it doesn't have `overscroll-behavior: contain`, so scroll events on the textarea bubble up to the message list, preventing the user from scrolling up to read history. Additionally, the message list div has no `overscroll-behavior` set, so iOS/desktop momentum scroll bleeds through to the page behind.

**Root Cause — Textarea Not Shrinking:**
The textarea uses CSS `resize: none` with a `rows={1}` attribute and `max-h-32`, but there's no JavaScript to auto-resize it. In some browsers, `rows={1}` sets initial height but the textarea never shrinks after growing because the browser doesn't reduce height automatically when text is deleted.

## BUG FIX PROMPT 9 OF 10
## Remove `maximum-scale=1` Accessibility Violation + Fix CSP

**Root Cause 1:**
`<meta name="viewport" content="width=device-width, initial-scale=1.0, maximum-scale=1" />` blocks pinch-to-zoom. This is an accessibility violation (WCAG 1.4.4) that affects users who need to zoom in to read content. It also fails automated accessibility audits (Lighthouse, axe). Modern iOS ignores this for users who need accessibility zoom, but Android browsers respect it and block zoom entirely.

**Root Cause 2:**
The Content Security Policy has `connect-src ... wss:` (bare wildcard WebSocket) which is overly broad. It should specify only `wss://*.firebaseio.com`. This doesn't break anything but is a security hygiene issue.
