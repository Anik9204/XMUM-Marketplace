FILE TO EDIT: artifacts/xmum-market/src/lib/userProfile.ts

PROBLEM:
When a user changes their Full Name in Settings, the new name is saved to
users/{uid}.fullName correctly — but all their existing listings in the
"listings" Firestore collection still carry the OLD userName field. The
ListingCard component displays "by {listing.userName}" which never updates.
So the home page and listing detail keep showing the stale name forever.

ROOT CAUSE:
The updateProfile() function only calls updateDoc on the users/{uid} document.
It never backfills the userName field on the user's existing listings.

BACKGROUND — how userName is written:
When a listing is created (PostPage.tsx), the userName stored on the listing
is derived from fullName like this:
  function getLastName(fullName: string): string {
    const parts = fullName.trim().split(/\s+/);
    return parts[parts.length - 1] || fullName.trim();
  }
  userName: userProfile?.fullName ? getLastName(userProfile.fullName) : (user.email?.split("@")[0] ?? "")

So "Taseen Ahmad" → userName is stored as "Ahmad".
The same derivation must be applied when backfilling.

THE FIX — two surgical changes to artifacts/xmum-market/src/lib/userProfile.ts:

CHANGE 1: Add a helper function at the top of the file (after the imports,
before the storagePathFromUrl function):

function deriveUserName(fullName: string): string {
  const parts = fullName.trim().split(/\s+/);
  return parts[parts.length - 1] || fullName.trim();
}

CHANGE 2: Modify the updateProfile() function. Currently it is:

export async function updateProfile(
  uid: string,
  data: Partial<Omit<UserProfile, "uid" | "createdAt">>
): Promise<void> {
  await updateDoc(doc(db, "users", uid), data as Record<string, unknown>);
}

Replace it with:

export async function updateProfile(
  uid: string,
  data: Partial<Omit<UserProfile, "uid" | "createdAt">>
): Promise<void> {
  await updateDoc(doc(db, "users", uid), data as Record<string, unknown>);

  // If fullName changed, backfill userName on all of this user's listings.
  // userName is a denormalized field on each listing document, derived as
  // the last word of fullName (same logic used in PostPage at creation time).
  // Skip report-held listings — Firestore rules block updates on them.
  if (typeof data.fullName === "string" && data.fullName.trim()) {
    const newUserName = deriveUserName(data.fullName);
    try {
      const snap = await getDocs(
        query(collection(db, "listings"), where("userId", "==", uid))
      );
      await Promise.all(
        snap.docs
          .filter((d) => d.data().isReportHeld !== true)
          .map((d) => updateDoc(d.ref, { userName: newUserName }).catch(() => {}))
      );
    } catch {
      // Non-critical — profile save already succeeded; listing backfill
      // failure is silent so the user is not shown a false error.
    }
  }
}

IMPORTANT CONSTRAINTS for this fix:
- The backfill only runs when fullName is part of the update payload AND is non-empty.
  Calls to updateProfile() for avatarUrl, whatsapp, wechat, showWhatsApp,
  showWeChat — which do NOT include fullName — will skip the backfill entirely.
  This is intentional and correct.
- Report-held listings are filtered out with .filter((d) => d.data().isReportHeld !== true)
  because Firestore rules block userName updates on held documents (only isArchived
  and status changes are allowed on held listings). Without this filter, those
  updateDoc calls would silently throw permission-denied — the .catch(() => {})
  handles it but it's cleaner to skip them upfront.
- The entire backfill is wrapped in try/catch and each individual updateDoc has
  .catch(() => {}) so a Firestore error on any single listing never surfaces as
  a profile-save failure to the user.
- No new imports are needed — getDocs, query, collection, where are already
  imported at the top of userProfile.ts.
